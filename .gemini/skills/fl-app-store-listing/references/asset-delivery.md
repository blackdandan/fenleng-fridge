# 素材与资质交付

## 市场目录

在项目约定的上架目录下按市场维护 `<market-id>/初次上架信息.md`、`<market-id>/版本上架信息.md` 与 `<market-id>/assets/`。assets 按实际材料使用 `icon/`、`screenshots/`、`builds/<version>-<build>/`、`copyright/`、`authorization/`、`qualification/`、`security-assessment/`、`privacy/`；不创建假证书或空白图片凑齐目录。长期材料清单写在初次文件，版本构建证据写在版本目录的构建记录。已满足正式打包与真机门禁的上传包才可归集；普通 release、过期候选或缺少门禁回执的包只记录源路径和缺口。不同市场的 assets 不共享、不交叉引用。

## 归档与 Git 边界

每个市场目录维护 `assets/README.md` 或等价清单，记录材料名称、用途、版本、来源、SHA-256、是否含敏感信息、是否进入 Git，以及平台上传/处理状态。通用规则、规格、模板和验证脚本只留在 Fenlengtechbase；应用名称、账号、审核回复、截图、构建号和真实资产只留在消费项目对应市场目录。

Markdown、生成脚本和体积合理的最终图标/截图可进入 Git。APK、AAB、IPA、xcarchive、dSYM、审核录屏、数据库导出、签名文件、身份证等敏感证照和超过仓库约定上限的文件不得提交；只在构建记录中保存受控位置、字节数和 SHA-256。不得为了归档修改或另建上传通道。

## 图标和截图

实际生成市场所需图标和 4–5 张截图。优先使用当前安装包截图或 Golden Test（用户也可能写作 GodenTest）从真实 Widget 导出，使用正常示例数据，保留可复现命令与版本。不得仅复制历史截图而声称为当前版本。

可在真实界面外添加标题、背景、边距和适度装饰，保持真实界面比例与交互内容，不虚构功能或遮住重要界面。用户要求 Golden Test 等确定性代码渲染时，通过项目现有渲染工具生成和导出；已有设计源优先无损导出。图标保持现有品牌，按规格输出直角 PNG，保留原件。

### 商品运营截图

应用市场截图不是尺寸合格的工程截图集合，而是一组按顺序浏览的商品信息。生成前先形成一行 Design Read，说明目标用户、商店浏览场景、视觉语言和每张图要帮助用户理解的结果；再为 4–5 张建立连续叙事，让每张只承担一个可从当前产品证实的核心能力。标题使用具体对象与动作，禁止未经证实的效率倍数、智能生成、用户规模、评价或行业领先表述。

构图应以真实 App 画面为主，可使用克制的标题、背景、裁切、边框和品牌节奏增强缩略图可读性，但不得用装饰替代产品内容。整组保持统一品牌骨架，同时通过真实状态、画面焦点、留白或产品窗口比例形成有理由的变化；不能只把同一模板换标题，也不能让空白页、导航抽屉、加载页或设置页在没有产品理由时占据主要商品位。优先展示有内容、有结果、可完成任务的状态。

用户明确要求审美提升、去 AI 味、视觉重做，或初版存在模板化、空洞、层级混乱时，读取并使用 `fl-taste` 做 Design Read、Taste Dials、anti-slop 和最终 visual review。`fl-taste` 只校准构图与审美，不能覆盖本 Skill 的市场规格、真实性、版权和材料边界。默认拒绝无产品理由的紫粉渐变、玻璃拟态、光晕、虚构设备、任意摄影、卡片堆叠和装饰性口号。

交付前同时检查两层：工程层验证尺寸、格式、字节数与可复现命令；视觉层逐张以全尺寸和缩略视图检查焦点、层级、换行、裁切、对比、真实功能、组图顺序和相邻图片变化。只有两层都通过才能标记为可上传；未实际查看生成图片不得声称视觉验收完成。

应用宝：`assets/icon/app-icon.png` 为 512×512、PNG、≤200KB；`assets/screenshots/01-*.png` 等 4–5 张，优先 1080×1920，最低 320×480，单张 ≤1M（上传器口径待核对）。逐张检查字形、截断、测试水印、比例和虚构数据。可用本 Skill 的 `scripts/validate_assets.py --assets <目录>` 验证 PNG 尺寸和字节上限；JPG 使用可用的图像库等价检查。

## 软著与授权

先搜索项目 knowledge root 的正式证书和软著记录，说明准确目录；只有申请/补正资料不等于证书。缺少时从用户指定文件或目录复制原件到项目知识目录，再复制市场所需原件到 `assets/copyright/`，以 SHA-256 核对副本；保留原始 PDF，不重制其签章。记录证书名称、版本、权利人、登记号、日期及与上架名称的差异。

软著交付必须同时包含原始 PDF 与从该 PDF 直接渲染的逐页图片。图片使用稳定页码命名，如 `<证书名>-第01页.jpg`；按 PDF 页数完整生成，不裁剪、不拼接、不加水印，也不把图片反向替代 PDF 原件。应用宝证书图片只接受 JPG、PNG 或 JPEG，单文件必须大于 0 且不超过 3072KB；在清晰度相当时优先选择体积更可控的 JPEG，不能交付超限 PNG。用 PDF 元数据核对页数，用文件哈希确认原件未变化，并登记每张图片的像素尺寸、字节数、格式和来源页码。逐张查看最终图片，确认方向正确，证书名称、软件名称、登记号、权利人和印章区域清晰，无黑块、空白、裁切或内容变化；未完成格式、字节数和目视检查不得标记为可上传。

根据实际权利人选择授权分支。企业：软著授权书与授权方营业执照。个人：软著授权书、授权方身份证正反面复印件、签名、红色手印和本人正在签署授权函的正面照片。个人分支应优先从组织资产目录查找姓名匹配的正反面复印件合页并复制到本次市场 `assets/authorization/`；只有单面文件时才分别归集人像面与国徽面。基本信息和材料清单只记录资产路径、格式、尺寸、哈希核验与用途，不转录身份证号码、住址、出生日期、有效期等证件正文。有效期记录永久有效或指定起止日期；不可自行默认。应用运营方与著作权人不同不能自行声称“不涉及授权”。

优先查 flbase 的 `knowledge/organization/README.md`、`knowledge/organization/assets/catalog.json` 或 Project Knowledge 对应入口，读取现有身份证、公章、签名和营业执照的使用约定。仅复制本次适用材料到 `assets/authorization/`，不把原件混入公开网站。现有法人手持照片不自动满足“正在签署授权函”要求；缺失照片和红手印向用户索取。

授权书按控制台正式模板生成；没有模板时用 [授权信息模板](../assets/authorization-info.md.template) 完成项目事实摘要和明确标注的可审阅草稿，列明缺失模板。生成资料不代表授权已生效。

## 安全评估

将已有正式报告及适用的上传图片归入 `assets/security-assessment/`。不存在正式报告时根据当前业务、代码和已执行验证生成有证据的安全评估报告草稿（Markdown，必要时 PDF 和逐页 PNG），明确哪些是事实、哪些未验证、是否需官方模板/流程。用户要求报告时必须实际生成，不能只留目录或路径清单；不能把内部自查冒充监管审定报告或为通过审核伪造结论。是否涉及社交、公开信息传播、私信、弹幕等按实际功能判断。

## 隐私整改

对照实际版本检查数据种类、目的、权限、第三方 SDK、存储、删除、注销入口、个性化与儿童相关说明。整改声明必须与现有实现和运营能力一致；例如没有 App 内注销入口不能编造设置菜单，邮件办理若需要新增运营承诺应取得明确确认。已授权发布时使用原有发布脚本，先构建验证，再部署并核对线上正文和哈希；保存已发布政策副本及核验记录到 `assets/privacy/`。不能以本地页面已修改代替部署完成，也不能把平台尚未执行的合规检测标为通过。
