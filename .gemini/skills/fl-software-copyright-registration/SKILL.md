# fl-software-copyright-registration

面向任意软件项目的软件著作权申请材料准备、源程序鉴别材料生成、自检审查与补正闭环。

## 适用与命中条件 (Routing Rules)

### 适用场景 / 意图关键词与信号
- **意图关键词**：`软著申请`、`软件著作权申请`、`软著补正`、`软件著作权补正`、`源程序鉴别材料`、`软件说明书`、`独立开发声明`、`软著材料自检`
- **工程信号**：`文件/目录: 7-知识产权管理/`、`文件/目录: docs/ip/`、`文件/目录: intellectual-property/`

### 排除条件 (Negative Signals)
- 用户明确要求商标申请
- 用户明确要求专利撰写
- 用户明确要求版权诉讼意见
- 用户明确要求法律结论或代理意见

## 执行方式

1. 根据本 Skill 的适用场景和排除条件确认任务边界。
2. 直接按照下方完整执行流程完成任务；只在当前步骤确实需要时读取对应 reference 或 asset。
3. 若存在 `scripts/`，优先使用其中的确定性程序，并检查其真实输出。
4. 不为内部步骤重新路由 Skill；由本 Skill 保持上下文并执行到完成。

## 目标

将任意软件项目的软件著作权申请过程标准化为可执行、可自检、可补正的 Skill，产出可直接提交或交给人工复核提交的最终材料包。可编辑 Word 和过程记录必须与最终交付材料分离；最终材料包至少包含申请填报信息摘要、软件说明书、源程序鉴别材料、主要功能描述、独立开发及原创性声明和材料清单。

本 Skill 不提供最终法律意见，不替代律师、代理机构或主管机构审查。涉及现行规则、提交入口、材料格式和期限时，必须核验中国版权保护中心或其他权威来源的最新要求。

## 适用场景

- 用户需要为一个软件项目准备中国软件著作权登记申请材料。
- 用户需要从项目源码中提取源程序鉴别材料，并生成 Word/PDF 交付件。
- 用户需要根据截图、功能描述和项目资料生成软件说明书。
- 用户收到软著补正通知，需要诊断退回原因并生成补正方案。
- 用户需要在正式提交前对材料一致性、源码完整性、页面饱满度、调试残留和补正风险进行自检。

## 不适用场景

- 商标、专利、版权诉讼、侵权判断或许可谈判。
- 要求伪造开发事实、注入无关代码、重复填充源码、制造原创性或规避真实审查。
- 仅需要普通产品 PRD、MVP 定义或工程编码交付的任务。

## 输入

- 软件基本信息：软件全称、简称、版本号、申请主体、开发完成日期、首次发表状态、开发方式。
- 项目类型：Web、移动端、桌面端、服务端、嵌入式或其他类型。默认建议选择一个端的代码作为源程序鉴别材料范围。
- 源码根目录：一个或多个真实项目源码路径。
- 排除规则：测试目录、生成代码、第三方依赖、脚手架、通用 CRUD、登录鉴权、实体类、DTO、配置文件等。
- 功能资料：核心功能、技术特点、运行环境、开发环境、安装与使用路径。
- 申请填报信息摘要：必须使用 `assets/software-copyright/application-info-summary.md.template`，并提供软件名称、版本号、环境信息、源程序量、开发目的、面向领域、主要功能和技术特点。
- 截图资料：用于说明书的界面截图及对应功能说明。
- 申请模式：首次申请或补正申请。
- 补正通知：补正阶段需提供退回意见原文、通知时间、要求期限和已提交材料。

## 交互与暂停规则

本 Skill 只能在两类状态停下：

1. **等待用户补齐阻断输入**：缺少申请主体、软件名称、版本、开发完成日期、首次发表状态、开发方式、源码路径、主体证明、补正通知、签字盖章材料等必须由用户提供或确认的内容。截图缺失时优先在 `work/` 的软件说明书 Word 中生成截图占位，并在最终清单中要求用户补图；只有截图缺失导致无法说明核心功能时才作为阻断输入暂停。
2. **完整任务完成**：`deliverables/vN/` 已生成当前轮次的 PDF/Markdown 最终材料包，Word 源文件、补正说明、第三方/开源说明和自检报告留在 `work/`，清单明确标记可提交文件、需人工签字盖章文件、需官方系统填写事项和剩余风险。

不得在“已生成草稿”“已生成 Markdown”“已生成过程说明”“源程序材料 high_risk 但未处理”时结束 Skill。此时必须继续执行以下动作之一：

- 向用户索取缺失事实、主体证明、签章材料或补正通知；截图缺失时优先生成带占位的 Word 说明书并要求用户在对应位置补图。
- 重新选择源码范围并重新生成源程序鉴别材料。
- 在 `work/` 生成或修改可编辑 DOCX；由该 Word 源文件转换 PDF，并将 PDF 写入当前轮次的 `deliverables/vN/`。
- 将无法自动处理的事项列为人工阻断项，并等待用户处理。

## 输出

- `docs/ip/software-copyright/work/`：可编辑 Word 源文件、Markdown 源文件、补正说明、第三方/开源说明、自检报告、扫描中间结果、风险分析和人工确认记录。
- `docs/ip/software-copyright/deliverables/`：按申请轮次隔离的最终交付材料根目录；根目录只保留版本索引，不直接混放交付件。
- `docs/ip/software-copyright/deliverables/vN/`：当前轮次的最终交付包。首次申请使用 `v1/`；用户明确反馈“被打回”或要求“补正”时，复制上一轮交付包并新建递增的 `vN/`，在新目录完成整改，不覆盖历史版本。
- 每个 `vN/` 目录只放该轮最终 PDF、申请填报 Markdown、材料清单和用户执行步骤；不得放可编辑 Word、补正说明、第三方/开源说明或自检报告。共享 `assets/` 和过程 `work/` 可以被引用，但清单必须明确当前轮次路径。
- 最终交付材料包默认包含：
  - 源程序鉴别材料：`源代码.pdf`，由 `work/` 中的源程序 Word 生成；若审计为 high_risk，仍可作为本轮复核交付件保留，但不得标记为可提交。
  - 软件说明书：`软件说明书.pdf`，由 `work/` 中的 Word 生成。若截图暂缺，Word 中必须预留截图位置，并在清单中列明用户需补充的截图。
  - 软件主要功能描述：`软件主要功能描述.pdf`，由 `work/` 中的 Word 生成。
  - 软件独立开发及原创性声明：`独立开发及原创性声明.pdf`，由 `work/` 中的 Word 生成。
  - 申请填报信息摘要：`申请填报信息摘要.md`；不生成 DOCX 或 PDF。
  - 材料清单与提交说明：`最终交付材料清单.md`。
  - 用户执行步骤文档：`用户执行步骤.md` 和可选 PDF，逐步说明用户需要确认、补充、签章和提交的事项。
- 补正说明、第三方/开源代码情况说明和提交前自检报告默认只保存在 `work/`；只有用户明确要求且官方入口明确需要上传时，才另行复制为当前轮次的交付件。

## 申请填报信息摘要规范

申请摘要使用 `assets/software-copyright/application-info-summary.md.template` 生成，工作源文件和最终交付文件均为 Markdown；不得另生成 DOCX/PDF。软件名称必须由申请人确认，模板以补正中“名称应明确”的经验提供 `XXXXApp` 示例，不得由 AI 擅自改名或把版本号重复拼入名称。字段定义和计数口径见 [`references/ip-application-info-summary.md`](references/ip-application-info-summary.md)。

以下约束是硬门槛，必须在复制到 `deliverables/vN/` 前通过 `scripts/validate_application_info.py`：

| 字段 | 硬约束 |
| :--- | :--- |
| 开发的硬件环境、运行的硬件环境、开发该软件的操作系统、软件开发环境 / 开发工具、该软件的运行平台 / 操作系统、软件运行支撑环境 / 支持软件 | 每项去除空白后不超过 50 字 |
| 源程序量 | 正整数行数 |
| 开发目的、面向领域 / 行业 | 每项去除空白后不超过 50 字 |
| 软件的主要功能 | 去除空白后 500–1300 字 |
| 软件的技术特点 | 去除空白后不超过 100 字 |

缺少字段、保留占位符、超过字数或格式不合法时，视为阻断输入，不得生成最终交付包。

## 执行步骤

1. 确认申请模式、项目类型、软件信息、材料范围和缺失项；扫描 `deliverables/` 的现有 `vN/` 目录，确定当前轮次。首次申请创建 `v1/`；每次用户明确反馈“被打回”或要求“补正”时，基于上一轮目录递增创建新的 `vN/`，不得在旧目录内覆盖整改。
   - 若缺少必须由用户提供或确认的信息，立即输出阻断输入清单并暂停；不得继续编造事实。
2. 用明确字段记录申请主体、软件名称、版本、开发方式、源码范围、第三方依赖、截图和补正状态；缺失事实保持阻断，不用自定义 Schema 假装已验证。
   - 用 `assets/software-copyright/application-info-summary.md.template` 创建 `work/申请填报信息摘要.md`，填入用户确认的事实；运行 `scripts/validate_application_info.py --input work/申请填报信息摘要.md --report work/申请填报信息摘要审计报告.json`，校验通过后才能复制为当前轮次的 `申请填报信息摘要.md`。
3. 生成材料计划，区分首次申请材料和补正材料。首次申请材料计划默认包含软件独立开发及原创性声明；如存在开源或第三方代码，应生成对应说明并交由用户确认。
4. 定义源码选择策略和排除规则。默认优先选择一个端的核心业务代码；只有在客户端、服务端或共享模块共同构成同一申请软件，且软件名称、版本和说明书能够一致解释其关系时，才允许纳入多端代码，并在源码筛选说明中标注各端来源。
5. 对确定性提取、格式化和审计任务，严格按以下顺序使用：
   - 先运行 `scripts/extract_source_material.py`（源代码材料强制移除 `import`/`package`/`using`/`namespace` 声明；若提取结果仍有此类声明或空白行则失败退出）。
   - 若公司已确认需要保护内部命名，紧接着运行 `scripts/pseudonymize_common_identifiers.py`；必须显式使用 `--apply`，默认仅预览。只替换已配置的内部通用标识符，替换名必须是与业务有明确关联、但不是行业通用词的等长名称；跳过注释、字符串、页眉、软件名称和公开框架 API。映射 JSON 只能留在 `work/`，不得进入 `deliverables/vN/`。
   - 运行 `scripts/review_source_material.py`，审计重复语义行、调试残留、结构完整性和页面饱满度；保留保密化前后的报告。
   - 再运行 `scripts/audit_common_identifiers.py`，只读统计 Bean、Domain、Manager、Service、Repository、Controller、Model、Entity、DTO、VO、Provider、Notifier、State、ViewModel、Config、Util、Helper、Factory、Builder、Adapter、Client、Request、Response、Result、Data、Base、API、DAO、Handler、Context、Widget、Screen、Page、View、Component、Route、Router、Theme、Event、Action、Store、User、Account、Item、List、Info、Value、Key、Type、Name、ID 等通用标识符及 CamelCase/snake_case 组成部分；该脚本不得改写任何源码或标识符，只输出人工复核报告。
   - 再运行 `scripts/fix_docx_metadata.py`
   - `scripts/build_deliverable_package.py --pdf-only --pdf-renderer reportlab --font-path <可嵌入中文 TTF> --deliverables-dir deliverables/vN/`
   - `scripts/render_docx_pdf.py`（从 `work/` Word 读取内容并嵌入中文字体生成 PDF；源代码按统一规范固定为 60 页）
   - `scripts/check-copyright-source.js`
6. 根据功能资料、截图和运行环境生成软件说明书与核心功能描述。若截图暂缺但功能可描述，继续在 `work/` 生成带截图占位的 `software-manual.docx`，并在最终清单中要求用户在 Word 对应位置补图；若截图缺失导致核心功能无法说明，才暂停并要求用户补充截图或确认无界面软件的替代说明材料。
7. 检查名称版本一致性、页眉页码、源码完整性、页面饱满度、调试残留和模板痕迹。
8. 生成并检查首次申请声明材料，确保声明中的开发方式、第三方代码、开源代码情况与用户确认事实一致。
9. 若处于补正阶段，解析补正通知，生成整改方案和补正说明；补正阶段应优先检查首次申请声明是否已提交，再决定是否生成更新版声明。
10. 将草稿、扫描报告和人工确认记录保存在 `work/`；不得把过程文件直接当作最终提交件。
11. 根据自检报告迭代材料，直到严重风险项关闭或明确记录为人工阻断项。若源程序鉴别材料为 high_risk，不得标记为“可提交”，必须重新选择源码页；无法自动重选时暂停并要求用户确认新的源码范围。
12. 在 `work/` 保留可编辑 Word 源文件；使用带可嵌入中文 TTF 的渲染器从源 Word 生成 `源代码.pdf`、`软件说明书.pdf`、`软件主要功能描述.pdf` 和 `独立开发及原创性声明.pdf` 到当前轮次的 `deliverables/vN/`。源代码统一排版规范为 A4、英文/数字使用 Courier New 9 磅、中文字符使用同字号嵌入式中文回退字体、固定行高 12.24 磅、每页 57 行、95 字符换行，当前源代码内容必须恰好生成 60 页（渲染后恰好 3420 行，即每页 57 行×60 页的真实源码行）；页码位于页面最上方居中且只显示纯数字（如 `1`、`2`），软件名称保留在页眉左侧，不得把页码放在右下角；源代码中不得出现 `import` 语句或空白行，使用 `scripts/fix_docx_metadata.py --remove-import-lines` 清除声明后，必须补入真实源码行，不得用空行占位。生成后必须渲染 PNG 检查中文无乱码、页数恰好为 60 页、正文无空白行、纯数字页码位置和 `import` 禁止项（签章页等官方原页除外）；申请填报信息摘要只复制 Markdown，不得把 Word 写入 `deliverables/vN/`。
13. 生成 `用户执行步骤.md` 和可选 PDF，逐步说明用户需要确认的软件名称、版本、申请主体、图标规格、截图补充、签字盖章、官方系统填报和最终提交材料；补正说明、自检报告和第三方说明仍留在 `work/`。
14. 输出最终材料清单，并标记哪些内容需要人工签字、盖章、上传或在官方系统填写。

## 成功标准

- 材料计划覆盖首次申请或补正申请的必要交付件。
- 过程文件与最终交付材料分目录保存；当前轮次 `deliverables/vN/` 只包含最终 PDF、申请填报 Markdown、材料清单和用户执行步骤，历史 `vN/` 目录保持不可变。
- 最终材料包包含可提交 PDF 或官方要求的等价格式，而不是只有 Markdown 草稿；可编辑 Word 全部可在 `work/` 找到。
- 最终材料包包含用户执行步骤文档，用户可以按文档逐项完成软件名称确认、图标准备、截图补位、签章、上传和提交。
- 首次申请材料计划默认包含独立开发及原创性声明，并在适用时包含第三方或开源代码情况说明。
- 软件名称、简称、版本号在说明书、源码材料、声明函和填报摘要中一致。
- 源程序鉴别材料来自真实项目路径，并保留可解释的核心业务逻辑来源。
- 源码审计报告明确列出重复率、截断风险、调试残留、页数饱满度和整改建议。
- 源码审计报告还应列出通用标识符频次和风险，但不得把通用标识符频次解释为抄袭结论；保密化映射只服务于减少命名泄漏，不改变核心逻辑，也不构成外部查重保证。本地脚本不连接外部登记机构或第三方代码数据库，不能保证外部查重结果。
- high_risk 源程序鉴别材料可以以 `源代码.pdf` 形式保留在当前 `deliverables/vN/` 供复核，但不得标记为可提交；源程序 Word 和审计报告必须留在 `work/` 并触发重新选材或人工确认。
- Skill 结束时只能是“等待用户补齐阻断输入”或“最终材料包已生成”；不得以草稿、过程文件或风险提示作为最终完成状态。
- 补正阶段能从退回意见映射到具体材料缺陷和整改动作。
- 交付版本按轮次隔离：首次申请为 `v1/`，每次明确补正递增一个 `vN/`，不存在跨轮次混放或覆盖历史交付件。
- PDF 中文字体必须可嵌入并经过 PNG 视觉检查；禁止交付仅在当前机器可显示、但 PDF 内没有中文字体资源的文件。
- 构建脚本在 `reportlab` 渲染后自动检查 PDF 是否存在嵌入式 TrueType 字体；字体参数缺失或字体资源检查失败时必须失败退出。
- 源代码 Word/PDF 的页码统一置于页面顶部居中且只显示纯数字；右下角不得出现源代码页码。
- 源代码统一规范检查必须包含：PDF 页数 `== 60`、渲染后恰好 3420 行真实源码且无空白行、正文 9 磅（Courier New + 中文回退字体）、固定行高 12.24 磅、每页 57 行、源码中不存在 `import` 语句；任一项不满足都不得标记为完成。
- 申请填报信息摘要必须使用 Markdown 模板，包含本 Skill 规定的 13 类字段，并通过 50 字、100 字、500–1300 字和正整数行数硬校验；未通过不得标记为完成。
- 本 Skill 引用的脚本和资源 均真实存在且有实质内容。

## 失败处理

如果缺少源码、软件信息、申请主体信息、主体证明、签字盖章材料或补正通知，暂停材料生成，输出缺失项清单和用户需要执行的动作。截图缺失时，优先生成带截图占位的 Word 说明书并列为用户后续动作；只有无法形成说明书主体内容时才暂停。

如果只生成了草稿或 Markdown 过程文件，继续执行材料转换、打包和自检；不得把该状态视为完成。

如果用户要求伪造事实、注入无关代码、重复填充源码或规避审查，拒绝该部分请求，并提供合规替代方案。

如果官方规则或提交口径无法确认，必须标记为“需人工核验”，不得把历史资料当作最新规则直接执行。
