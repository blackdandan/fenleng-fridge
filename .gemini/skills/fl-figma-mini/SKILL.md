# fl-figma-mini

以 `figma-map.md` 将 Figma 节点、行为 spec、小程序页面/组件、页面状态、截图环境和验收证据绑定起来，持续推进微信小程序的设计稿驱动 UI 实现。

## 适用边界

- 用户要求在微信小程序中按 Figma 设计稿实现、还原、补全、换肤或排查页面、组件和状态时使用。
- Fenlengtechbase 的标准实现层是 Taro、React、TypeScript 与 pnpm workspace，微信端目标为 `weapp`；页面和 UI 组件位于应用组合根与 `packages/ui-kit`，平台 API 由 Adapter 封装。
- 原生 WXML/WXSS 项目可以复用本 Skill 的节点映射和截图验收方法，但若不符合 Fenleng 小程序工程标准，必须在结果中标记为“非标准技术栈”，不得声称通过 Taro 架构门禁。
- 本 Skill 负责 Figma 节点到小程序代码的实施循环、截图采集和视觉保真门禁；Fenleng Token、主题、组件和可访问性规则由 `fl-ui-design-system` 提供，业务行为仍以项目 spec 为准。
- 纯后端、纯业务逻辑、Flutter/Web 非微信小程序渲染目标，以及没有设计稿依据的开放式视觉设计不使用本 Skill。

## 输入

- Figma 文件或可精确读取的 `node-id`；
- 项目行为 spec、目标小程序工程和待实现范围；
- 已有或待创建的 `docs/mini-program/figma-map.md`；
- 设计基准宽、设备/模拟器 profile、状态栏与小程序导航栏是否包含在截图中的约定；
- 项目的 `rpx`/`px`/适配工具约定、页面入口和可重复构造目标状态的数据入口；
- 可用的 Figma MCP、项目已有的微信开发者工具/自动化截图入口、Python 3 与 Pillow。不要假设项目一定安装了某个小程序自动化库。

## 输出

- 按已确认范围实现的小程序页面、组件、交互状态和可重复测试入口；
- 更新后的 `docs/mini-program/figma-map.md`、页面明细、共享组件清单和阻塞清单；
- Figma 与小程序渲染截图逐块对比的数字证据、差异图和截图环境记录；
- 截图回归、开发者工具/真机复核和非基准尺寸检查结果；
- 尚未验证、需要人类决策或依赖外部团队的明确事项。

## 执行步骤

1. 读取项目指导文件、行为 spec、现有页面骨架、同类组件和截图入口。涉及 UI 实现时，按 `fl-ui-design-system` 的规则读取 Design System Project Knowledge；Taro 项目同时读取 `knowledge/mini-program/README.md`、平台能力矩阵和相关接入契约。无法读取时必须报告证据缺失，不得声称完成规范合规。
2. 确认源码层、运行层和依赖方向：Taro 页面/组件使用 Application State，`domain` 与 `application` 不引入平台 SDK，平台差异进入 Adapter；不要修改编译产物来代替源码实现。
3. 检查依赖与环境：Figma MCP 是设计读取基础；截图采样需要 Python 3 和 Pillow；开发者工具或项目自动化入口用于重复截图；真机复核需要微信开发者工具的真机预览或项目已有设备链路。缺失路径标为“未做该级门禁”，不得默认通过。
4. 建立或读取映射清单。若缺少 `docs/mini-program/figma-map.md`，复制 `assets/figma-map-template.md` 并按页面索引、共享组件、backlog、页面明细分层填写到 `docs/mini-program/` 目录。
5. 在首次实现前与用户确认一次范围、优先级、可疑 `node-id`、设计基准宽、适配方式、截图 profile，以及外层是否已经处理安全区/导航栏。范围与截图基准未确认时，不进入自治实施循环。
6. 将已确认的待做行登记到项目任务列表，从最高优先级 `⬜` 行开始逐行执行：读 spec、按 `node-id` 取 Figma、复用现有小程序骨架、实现页面/组件、提供可重复状态入口、截图、验收、回填状态。
7. 每行完成前执行覆盖驱动验收：枚举当前准节点的顶层子节点；逐块测背景、文字、图标/图片、控件、分割线和浮层；反向检查渲染中是否多画、重复、错套容器或受平台默认样式污染。所有适用块都有证据后才可标记 `✅`。
8. 先完成 Figma 保真采样，再生成或更新项目截图回归基准；随后在微信开发者工具或真机上复核字体、图片、原生控件、安全区、滚动和系统差异。存在适配层时，再用明显不同于基准宽的 profile 检查一次。
9. 回填 `docs/mini-program/figma-map.md`、页面明细、截图环境、采样结果和任务状态，然后继续下一行。只有遇到原生能力选型不明、spec 真缺口、截图入口不可用，或需要 commit/push/PR 等外发动作时才暂停请求用户决定。

## 阶段 0：建图与范围确认

每个 UI 模块维护一张瘦索引，惯例结构如下：

```text
docs/mini-program/
├── figma-map.md
├── components.md
├── backlog.md
└── pages/<name>.md
```

- 一行代表一个可独立实现和验收的交付物，不等于一个 Figma 节点。
- 不同行为或状态需要独立代码分支和验收时拆行；同一交付物的多个 tab 或状态可在页面明细中登记对应 `node-id`。
- 状态使用 `✅` 完成、`🔶` 进行中、`⬜` 待做、`⏳` 整页占位；缺 `node-id` 使用 `TODO` 并进入 backlog。
- 推进类型默认 `🤖`。仅选型、spec 决策和外发动作标为 `🧑`；缺 node-id、缺截图入口或外部依赖属于阻塞，不属于人工推进类型。
- 新增或删除页面只改索引；单页细节写入 `pages/`；跨页复用组件写入 `components.md`；阻塞解锁后从 `backlog.md` 删除，不保留历史流水账。

截图基准必须在第一个实现前明确：设备 profile、设计基准宽、页面可视高度、DPR、系统字体、状态栏/导航栏裁切、安全区、`rpx` 或 `px` 的转换规则，以及是否存在外层统一缩放。基准宽下比例通常接近 1，截图回归无法发现漏适配或双重适配，因此非基准 profile 是独立门禁。

## 阶段 1：逐行自治循环

每个已确认行按以下顺序推进：

1. 读取行为 spec，明确字段、边界、交互、网络/本地数据和状态联动。
2. 使用精确 `node-id` 获取节点结构和截图，视觉以 Figma 为准，行为以 spec 为准。
3. 检查现有小程序组件、主题 Token、页面壳、tab、弹层、`scroll-view`、安全区和图片处理方式，优先复用而不是重造。
4. 实现目标状态，并建立可重复到达该状态的入口：测试数据、query 参数、调试开关或项目既有 fixture 均可；不得依赖一次性手工操作而无法复核。
5. 在固定 profile 下采集小程序截图，与 Figma 图保持相同坐标系；必要时先裁掉双方都不属于页面内容的系统区域。
6. 使用 `assets/fidelity_sample.py` 做本地数字采样，再查看并排图或差异图定位问题。脚本结果优先作为筛选依据，避免把完整高清截图反复放入模型上下文。
7. 采样通过后运行项目已有的截图回归或重新固化基准，再做开发者工具和真机复核；对非基准 profile 做独立检查。
8. 记录证据并回填 `✅`；任何一个适用门禁未完成，保持 `🔶` 并写明未完成原因。

## 小程序实现约束

- Taro 项目修改 TSX/主题 Token/组件源码和应用组合根，不直接修改构建后的 WXML、WXSS 或平台临时目录。
- 读取项目既有的 `rpx`/`px` 适配工具和设计基准，不自行假定 750 设计稿或固定换算；字号、行高、间距、圆角、边框、图片尺寸和阴影分别记录适配方式。
- 页面和共享 UI 组件只渲染 Application State 并发送 User Action；登录、支付、存储、网络等平台能力通过契约和 Adapter 使用，不在页面散落平台判断。
- 主动检查微信默认控件样式，尤其是 `button`、`input`、`textarea`、`swiper`、`scroll-view`、图片裁切和原生导航栏；与 Figma 不符时优先通过项目允许的样式/组件封装消除默认差异。
- 明确安全区、刘海屏、底部手势区、状态栏、导航栏和键盘弹出后的布局边界。Figma 未包含系统区域时，不要把系统区域差异错误归因于页面 UI。
- 复杂 tab、长列表、空/加载/错误/成功/禁用/权限不足等状态应按 spec 分支登记；不可只实现设计稿中的静态默认态。
- 图片、字体、图标和本地资源必须走项目实际资源路径验证；截图中出现占位图、字体回退、emoji 替代图标或网络资源未加载时，不得标记保真通过。

## Figma 节点读取约束

- 大文件只按精确 `node-id` 读取结构和截图；不要依赖整页搜索、当前选区或整文件截图。
- 一个父锚点足以开始时，读取其节点树并按子节点名称识别状态变体，不反复向用户索要每个子节点 id。
- 截图先保存到项目临时目录再检查，用完后移除；报告中保留可复现的截图 profile 和来源说明。
- Figma 连接是单通道时串行读取，避免并发请求互相挤占而超时。
- 插件断连、开发者工具断连、截图入口失败或构建失败属于异常暂停；修复或明确等待，不得把未运行的检查视为通过。

## 保真验收门禁

使用 `assets/fidelity_sample.py` 将“Figma 参考图 vs 小程序同态截图”的对比从肉眼判断变成数字判断：

- `compare FIG REN [--out diff.png]`：统一尺寸检查、平均绝对通道差、P95 差异、最大通道差和超阈值像素比例，并可生成差异图；
- `point IMG XF YF`：采样关键位置的颜色 hex；
- `glyph IMG X0 Y0 X1 Y1`：测文字可见高度并估算设计基准下的字号，结果仅作辅助，不替代字体人工复核；
- `bbox IMG X0 Y0 X1 Y1 HUE`：测图标、图片或色块的包围盒与位置比例；
- `sxs FIG REN Y0 Y1 [--out compare.png]`：生成局部并排图作为人工复核兜底。

每行验收遵循四条规则：

1. 用当前准节点的直接子节点生成覆盖清单，背景层始终算一块。
2. 逐块选择对应采样：背景核层次和色相，文字核颜色和字号，图标/图片核大小、位置、裁切和叠放，控件核状态与默认样式。
3. 反向检查渲染是否存在 Figma 没有的重复元素、多余装饰、错误白卡、默认按钮样式、错误裁切或系统区域误入。
4. 每个适用块给出 `✓/✗` 和数字；有一块未核就不能标记完成。整体相似度不能替代关键块覆盖。

采样阈值应结合项目截图 profile、字体和图像内容确定，并在报告中写明，不得套用一个对所有页面有效的固定阈值。像素差异只能证明图像差异，不能单独证明交互、滚动、无障碍或真机兼容性。

## 截图回归、真机与平台差异

- Figma 保真采样、截图回归和真机复核是三种不同结论，必须分别报告；截图回归只证明相对历史截图没有变化，不证明符合 Figma。
- 截图回归至少固定：页面入口、测试数据、状态、设备 profile、DPR、滚动位置、字体资源、网络/缓存条件和系统区域裁切。
- 开发者工具截图可以用于快速回归，但不能替代真机复核；真机至少检查字体回退、图片加载、safe area、键盘、滚动惯性、原生组件和系统导航差异。
- 非基准 profile 应选择能暴露适配问题的宽度或设备，不要只在设计稿同宽下验证。
- 若只能人工截屏，仍需记录设备、版本、入口、状态和截图文件；未配置自动化不等于无法验收，但要明确自动化门禁未做。

## Token 与上下文成本控制

- 图片和截图尽量留在本地，由脚本先计算；模型只接收摘要指标、差异区域和必要的局部裁剪。
- 同一个 `node-id`、同一个已通过区域和同一张截图不要重复读取；修改后优先重采样受影响区域。
- 构建或截图工具输出应截取关键错误与结果，避免把无关的完整日志放入上下文。
- 只有在数字结果异常、字体/裁切/层级难以由指标判断时，才加载并排图或局部原图进行视觉复核。

## 成功标准

- 已确认范围内的每个交付物都能由 `docs/mini-program/figma-map.md` 追踪到 `node-id`、spec、实现、截图 profile 和状态；
- 每个 `✅` 行都具有顶层区块覆盖清单，以及适用的颜色、字号、尺寸、位置、裁切或状态数字证据；
- Figma 保真、截图回归、开发者工具/真机复核和非基准 profile 复核分别报告，没有互相替代；
- 项目既有组件、Fenleng Token、小程序端设计规范和尺寸适配约定得到复用；
- 未完成项准确进入 backlog 或用户决策清单，没有把缺失依赖、字体回退、占位资源或未运行检查默认为通过。

## 失败处理

- 缺 `node-id`、截图入口、测试数据或资源：登记到 `backlog.md`，继续其他已确认且可执行的行；
- Figma MCP、开发者工具、真机或构建链路断连：暂停受影响路径，报告具体错误和已完成证据；恢复后从当前行继续；
- 无 Python/Pillow：可以继续实现，但不得声称通过数字保真门禁；
- spec 与 Figma 冲突：行为遵循 spec、视觉遵循 Figma；无法同时满足时列出冲突并请求用户决策；
- 原生组件与自绘组件选型不明、spec 真缺口或需要外发：停止该决策点，不替用户猜测或扩大授权；
- 任一顶层区块缺少证据、采样失败、截图环境不一致或真机未复核：保持 `🔶`，不得标记 `✅`。
