# Clarification Gate Rule (疑点审计规则)

本规则用于防止 Agent 在需求、规则或实现细节存在疑点时靠猜测推进，确保技术设计与业务目标的精确一致。

## 1. 触发范围

创建或更新以下任一内容前，必须先执行本规则进行疑点审计：

1. 正式 Spec。
2. Implementation Plan。
3. HTML Preview。
4. 生产代码。
5. 对外 contract、公开 API、资源配置、点击契约、请求参数或数据模型。

## 2. 必须澄清的情况

以下任一情况出现时，必须先停止当前产出并向用户提问：

1. 用户描述中存在相互冲突的数字、公式、范围、默认值或流程。
2. 用户描述与已读规则、现有 Spec、现有 Plan、现有代码事实不一致。
3. 同一句需求存在两种及以上合理解释，且不同解释会影响 contract、数据请求、UI 行为、测试边界或对外兼容。
4. 需要新增或修改公开 API、contract 模型、资源配置、点击契约、请求参数或数据模型，但默认值、关闭态、异常态或兼容策略未明确。
5. 截图、参考图或“样式参考”会影响颜色、间距、图层顺序、线型、字号、对齐方式等生产 UI 参数，但尚未转化为明确可审核规则。
6. Agent 准备在 Spec / Plan 中写入“按 X 理解”“暂定”“后续确认”“以实现为准”等假设性内容。

## 3. 澄清方式

1. 每次只问 1 个最高影响疑点，除非多个疑点互相强绑定，必须一起确认。
2. 提问前必须说明该疑点为什么会影响实现或验收。
3. 如果存在多个可选解释，必须列出选项和影响，并标出推荐选项，但不得把推荐选项当作已批准事实。
4. 用户明确回答后，才能把该结论写入正式 Spec 或 Plan。
5. 若用户要求“你自己定”，必须把该决策写入 Spec 的“用户授权 Agent 决策”条目，并说明影响面。

## 4. Spec 前疑点清单

创建或更新正式 Spec 前，必须先完成一轮疑点审计：

1. 列出已发现疑点。
2. 标记每个疑点状态：`已确认`、`需用户确认`、`不影响本轮`。
3. 只允许把 `已确认` 或 `不影响本轮` 的内容写入正式 Spec。
4. 仍存在 `需用户确认` 的疑点时，不得写正式 Spec；只能继续提问。

## 5. 禁止行为

1. 禁止用“保守假设”“按更具体的数字”“按常见做法”替代用户确认。
2. 禁止把矛盾需求中的任一侧静默选为事实。
3. 禁止通过在 Spec 中写“后续确认”绕过澄清。
4. 禁止在未确认截图细节时，把截图视觉参数反推为生产参数。
