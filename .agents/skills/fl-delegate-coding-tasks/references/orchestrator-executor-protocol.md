# 主编排者与执行者协议

用户已在当前主会话显式启动委派后适用。

## 唯一交互链

```text
用户 ↔ 当前会话主编排者 ↔ Delegation MCP Broker ↔ 执行者
```

MCP Broker 只是有界通信与进程控制通道，不拥有产品或审批决策。执行者不得直接询问、请求批准或等待用户输入。执行者只接收主编排者冻结的任务，只向主编排者报告。主编排者在用户已授权范围内拥有执行审批、方案选择、范围收窄、整改、重试、换执行者、停止和接管权。

主编排者不得用内部审批扩大用户授权。出现新的产品决策、公开契约、敏感权限、破坏性操作、生产写入或其他超出原授权的事项时，主编排者先停止执行者，再自行向用户请求授权；不得让执行者越过主编排者直接询问。

## 分发前冻结

每个任务必须由主编排者冻结以下字段：

```text
任务类型：目录中的稳定 task id
风险：low | medium | high | critical
模式：read-only | write | verification | review
目标：唯一可验收结果
允许路径：可读取或修改的相对路径
禁止路径：不得修改的路径
必读上下文：开始前必须读取的文件
验收：主编排者将检查的行为
验证：主编排者将独立运行的命令
已批准动作：执行者可以直接执行的动作
停止条件：必须停止并报告的情形
```

执行者收到任务即代表主编排者批准执行“已批准动作”，不需要再次询问用户或主编排者。任务没有声明的写入、命令、路径、外部状态变化或风险升级均视为未批准。

## 执行者终态

执行者只能向主编排者返回以下状态：

- `completed`：冻结目标已完成并停止。
- `blocked`：缺少输入、权限或环境条件。
- `needs-orchestrator-decision`：存在多个合法方案，需要主编排者选择。
- `scope-expansion-requested`：必须扩大路径、契约或动作才能继续。
- `verification-failed`：实现已完成但指定验证失败。
- `failed`：执行器、工具或 Session 失败。
- `stopped`：已按主编排者要求或停止条件终止。

`completed` 必须保持紧凑，总文本不超过 2000 字符：

```text
状态：completed
修改路径：仅列实际修改路径，最多 50 项
Diff 统计：一行
验证：命令、退出码和不超过 200 字符的摘要，最多 20 项
未完成项：最多 10 项；没有则为空
需要主编排者处理：没有则为“无”
```

不得返回完整 Diff、源码、stdout、stderr、工具事件、测试日志或过程复述。主编排者可以直接读取工作区，需要证据时按路径或失败命令获取。

非 `completed` 状态使用紧凑结构：

```text
状态：<稳定状态>
证据：<最小事实、路径或失败命令>
问题：<一个明确问题>
候选方案：<零到多个有限方案>
建议：<执行者建议，可为空>
需要主编排者决定：<是或否；不得写“需要用户确认”>
```

非完成状态同样不得超过 2000 字符。错误证据只保留最相关片段，不复制完整日志。

执行者不得输出完整思考过程、向用户说话、创建新的委派任务或启动其他执行者。

## 主编排者处理

- `completed`：先检查 `git status --short`、`git diff --stat` 和修改路径，再按风险读取必要 hunks；不得默认把完整 Diff 放入上下文。
- `blocked`：主编排者补充已有上下文、修复环境、换执行者或接管；只有缺失用户授权时才询问用户。
- `needs-orchestrator-decision`：主编排者在原授权内选择方案，并以同一 Session 的新冻结轮次回复。
- `scope-expansion-requested`：主编排者判断扩展是否仍在用户授权内；在授权内可批准并重写边界，否则停止后询问用户。
- `verification-failed`：先核对证据，再发出最小整改轮次或接管。
- `failed`：先检查当前工作区，避免重放已完成修改，再决定恢复、重建或换执行者。

任何状态都不能自动转发给用户。主编排者先解释、吸收和决策，只在确有用户控制点时形成面向用户的问题。

## 分层审查

主编排者按以下顺序获取证据：

1. Broker 收据中的状态、修改路径、越界标记和验证摘要。
2. `git status --short`、`git diff --stat`、`git diff --name-only`。
3. 任务允许路径中的实际修改 hunks。
4. 只有出现越界、公共契约、高风险修改、统计异常或验证矛盾时读取完整相关 Diff。

二进制文件、大型生成物和无关用户修改只核对路径、大小、摘要或生成来源，不把内容灌入主编排上下文。

## 不由执行者决定

- 用户需求和产品行为选择。
- 总体架构、跨项目边界和最终契约。
- 是否接受越界修改或失败验证。
- Commit 范围、Push、Tag、发布和生产操作。
- 最终验收与交付结论。

以上决策完成并被冻结为具体实现任务后，其中边界明确的读取、修改或验证动作仍可委派。
