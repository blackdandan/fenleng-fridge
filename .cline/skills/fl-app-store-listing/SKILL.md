# 应用市场上架资料

## 输入

用户明确的应用上架意图、目标项目和市场，以及项目已有产品资料、隐私政策、备案和资质材料。仅出现市场名称或工程中已有资料目录不触发；用户显式调用本 Skill 时按其请求执行。

## 执行步骤

1. 未指定市场或要求继续扩展渠道时，先读 [渠道发现与准入](references/channel-discovery.md)，用项目历史记录、当前官方要求和账号实际权益确定可推进渠道与受阻原因；不要把账号认证当作应用可上架。读取项目约定和已有上架资料，识别实际应用；多应用仓库按应用隔离。优先沿用明确约定的目录，否则使用 `docs/app-store/<market-id>/`，多应用再增加 `<app-id>/`。市场目录是交付边界：Apple、应用宝及其他市场不得共用上架正文、构建记录或素材目录，也不得从一个市场文件链接另一个市场文件作为提交依据。
2. 每个市场固定拆为三层：`初次上架信息.md` 保存创建市场记录和首次提交所需的长期字段；`版本上架信息.md` 保存每次发版都要复核或填写的版本字段；`assets/builds/<version>-<build>/构建记录.md` 保存该市场本次构建制品与上传状态。初次提交需要三层齐备，后续发版只新建/更新当前市场的版本文件和构建目录；应用级事实、政策、分类或长期素材变化时才更新该市场的初次上架文件。
3. 只读取本次市场的 reference 和模板。应用宝使用 [应用宝要求](references/tencent-myapp.md)、[应用宝初次上架模板](assets/tencent-myapp-initial.md.template) 与 [应用宝版本上架模板](assets/tencent-myapp-release.md.template)；Apple App Store 使用 [Apple App Store 要求](references/apple-app-store.md)、[Apple 初次上架模板](assets/apple-app-store-initial.md.template) 与 [Apple 版本上架模板](assets/apple-app-store-release.md.template)。项目公共知识可作为事实来源，但交付时将实际值写入目标市场自己的文件，不能用根目录混合 `基本信息.md` 代替，也不能把一个市场的规则、选项或状态复制到另一个市场。
   其他已支持渠道按平台分别读取：
   - vivo 中国站：[要求与流程](references/vivo.md)。
   - 华为 Android：[要求与流程](references/huawei-appgallery.md)。
   - 华为 HarmonyOS：[要求与流程](references/huawei-harmonyos.md)。鸿蒙构建记录按实际发布包和证书/Profile 记录，不能套用 APK 或 Apple 字段。
   - 荣耀：先读 [资格与流程](references/channel-discovery.md#荣耀应用分发资格与后续-apk-提交)，确认 APK 权限后才准备该市场实际表单资料。
   新渠道可共用 [三层资料模板](assets/additional-market.md.template) 的结构，但必须分别输出目标市场自己的实际资料；模板共用不代表规则或素材共用。
4. 每个文本字段使用独立标题和纯文本代码块，代码块中只放可粘贴内容；状态、来源、字数、待办放块外。选项字段记录实际选择；缺失字段不生成含占位符的可复制块。素材记录实际文件路径、规格、核验结果和缺口，在市场目录创建 `assets/`，生成和归集实际上传文件；详见 [素材与资质交付](references/asset-delivery.md)。市场截图既是规格制品也是商品运营素材，必须结合产品语境、真实能力和连续浏览顺序完成构图与逐张视觉验收；用户要求更好看、去模板化或现有素材审美不足时结合 `fl-taste`，但不得夸大功能或让装饰遮挡真实界面。不得仅列出外部原件路径代替交付。
5. 后续发版时只更新对应市场的 `版本上架信息.md` 和新建的 `assets/builds/<version>-<build>/`；只有目标市场的应用级事实、素材、资质或政策发生变化时才更新同市场的 `初次上架信息.md`。同一字段只属于一层：长期字段不复制进版本文件，版本与构建状态不回写到初次文件。保留用户编辑及来源，不提前创建未使用市场的目录。
6. 检查项目隐私政策及 App 的实际采集、SDK、权限、注销和儿童/个性化处理。发现缺口时形成具体整改内容；用户已授权整改与发布则执行并复用项目已有发布通道，上线后核对 HTTP、静态正文和内容哈希。缺少真实业务事实时仅问缺失事实，继续独立材料工作，不编造服务承诺。
7. 对照所选 reference 检查字段覆盖、文案长度、事实一致性与实际素材尺寸/格式/大小。提交前必须建立“应用名称一致性矩阵”，逐字核对市场创建/提交名称、Android 默认及各 locale `app_name`、最终 APK 安装名称、iOS `CFBundleDisplayName`/`CFBundleName`、最终 App/IPA 安装名称、软件著作权证书软件名称和 APP 备案名称，并记录每个值的真实来源。中国大陆渠道以“市场创建/提交名称＝对应安装包安装名称＝APP 备案名称”为名称硬门禁；任一未知或不一致均不得标记为可提交。软著名称仍必须真实记录和显著提示差异，但仅在市场当次明确要求软著同名或 Owner 将其设为门禁时阻断，不能把历史审核文案自动升级为所有项目的永久规则。海外市场不适用中国 APP 备案时记录“不适用”，不得伪造备案值。Android 安装包记录包名、版本、ABI、签名摘要、字节数和 SHA-256；Apple 构建记录 Bundle ID、Marketing Version、Build Number、签名身份、Profile、Archive/IPA 状态和 SHA-256。两者均区分“本地存在”“签名可验证”“已通过项目正式打包/真机门禁”“平台已处理/检测”；缺证据时不得标记为可上传或平台通过。按 Unicode 字符数报告本地文案长度，平台计数不同则以表单为准。引用的市场要求是有日期的资料快照；用户要求最新规则或当前提交判断时核验官方要求并记录来源，不把历史快照当实时规定。
8. Apple `初次上架信息.md` 顶部必须生成首次提交总清单，按顺序引用三层产物：价格/地区 → App 隐私问卷和隐私政策 URL → 本地化产品页文案 → 真实设备截图 → 版本/构建号对齐 → 上传并选择构建 → 加密出口合规 → 审核登录/联系信息 → 发布方式 → 清除错误并加入审核。每项给出所属文件、可复制值、当前状态和下一步；“保存”不等于“加入审核”。无内购/订阅时，App Store 服务器通知 URL 和 App 专用共享密钥明确记为留空/不生成，不用普通网站 URL 占位。

## 输出

每个目标市场独立交付 `初次上架信息.md`、`版本上架信息.md` 与 `assets/`。`assets/builds/<version>-<build>/构建记录.md` 记录构建制品、签名、哈希、上传与平台处理状态；长期图标、截图、隐私和资质材料仍放在该市场自己的 assets 子目录。Apple 截图不得用 Android 或其他市场运营图直接冒充，Archive/IPA 不因本地存在就自动视为已上传或审核通过。

## 完成标准

可取得的信息和文件均已生成/归档，截图、图标和软著逐页图片的尺寸与大小已验证且逐张目视检查，软著 PDF 原件已保留并核对页数与哈希，已有用户资料保留。报告缺失事实、真实签署照片、手印和官方文件等人工事项；这些缺失只能标为等待补充，不能用占位文件冒充已完成。授权的隐私整改需完成发布和线上核验后才能宣称完成。

## 硬约束

准备资料不自动授权提交市场审核或发布应用；用户明确要求继续上架时按已授权的目标市场和范围推进，遇到宿主要求的协议确认、验证码或敏感材料传输限制才在具体动作处处理，不反复索取已有授权；用户对隐私政策整改和部署的明确授权按会话持续有效。使用真实证照及授权资产，读取资产使用契约；起草授权书不等于已签署。签章或代签若仍需具体文件授权，先完成可审阅稿，再一次性请求确认；不能合成本人正在签署的照片或虚构红手印、评估通过及备案结论。

新增市场时在标准源仓增加独立 `references/<market-id>.md`，正文追加按需链接；确有输出需求时才增加对应模板。市场 reference 保存要求，共用主体事实留在消费项目，避免市场间重复维护。业务项目使用时补充项目资料，不自行修改受管 Skill。
