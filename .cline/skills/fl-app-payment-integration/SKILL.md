# fl-app-payment-integration

将目标 App 接到矩阵公共支付能力，以真实订单与权益验收结果作为完成依据。

## 输入

- 唯一目标项目、App 根目录、发布渠道及购买对象。
- Owner 确定的商品、价格、计费模式和权益；项目现有身份与正式签名资料。
- 带 commit/ref 的 Shared Platform 与 Client SDK Knowledge、运行环境及渠道后台事实。

## 输出

- 目标项目的支付接入配置、SDK 组合根和购买/恢复入口。
- 项目 Knowledge 中不含敏感值的渠道身份、商品绑定、配置引用及逐场景验收证据。
- 已验证的完成状态，或明确区分本地完成与渠道/真实交易待办的结论。

## 执行步骤

1. 从目标 Manifest、实际构建与 Knowledge 确认产品、端型、身份、用户归属与环境；从 Owner 输入或既有商业配置取得商品/价格，缺少时仅推进不依赖定价的公共能力，不自行定价。
2. 读取 Shared Platform 的支付接入与 Sandbox Runbook、Client SDK 对应支付包，并记录来源 ref。确认 Adapter、会话载荷、原生实现、订单恢复、权益查询与退款边界的真实能力；不可将 Adapter 存在、Mock 通过或商户产品开通当作全链路完成。Flutter workspace 要检查所有引用 `fenleng_sdk_flutter` 的成员，将核心 SDK、支付包及依赖核心 SDK 的共享模块固定到同一 Git ref；在没有本机 path override 的消费者环境运行 `flutter pub get` 并核对 lock，避免同一 package 被解析到不同提交或本地目录。
3. 涉及支付宝 APP 支付时读取 [支付宝接入与验收](references/alipay-app.md)，创建阶段即完成该文的公钥准备、后台填写与下载交接，不把可自动处理的公开资料留给 Owner；微信 APP 支付读取 [微信接入与验收](references/wechat-app.md)。iOS/iPadOS 内购必须读取 [Apple StoreKit 快速接入](references/apple-storekit.md)，核实共享原生实现、商店商品、验证归属、自动续期和恢复购买；其他渠道依据其官方接口及当前平台能力处理，不把支付宝的申请或签名规则推广到所有渠道。数字会员必须读取并执行 [数字订阅渠道矩阵](references/digital-subscription-channel-policy.md)，在组合根和购买方法同时约束渠道。
4. 首次收费或调整商品、渠道、续费、退款、经营主体及相关法律规则时，读取 [购买协议、同意与变更](references/purchase-agreements.md)，结合产品和组织事实生成或复核协议，并在产品官网维护正文及历史版本；按国内/国外正式渠道分别核对购买页告知、明确同意与订单证据；国外无法律或商店强制依据时不新增确认流程，不以隐私同意或支付渠道授权替代购买约定。
5. 在应用级配置 Application、Plan、PriceOption、权益定义、Provider registration、商品绑定和 Secret 引用；按具体 PriceOption 验证 readiness。保留现有凭据恢复入口；凭据值不进入项目知识或日志，按本次授权范围处理写入与线上配置。
6. 新建或调整购买、待支付、权益及续费页面时，先使用 `fl-ui-design-system`，按其 Knowledge 读取协议加载 Fenleng Design System 的 Token、主题、组件和视觉验收规范，再读取目标 App 已有设计约定及代表性页面。以 FL 规范为基线，复用当前 App 已映射的品牌语义 Token、字体、间距、布局和组件；不得另起支付页私有视觉体系。现有 App 与 FL 规范冲突时标明具体差异，在本次范围内处理；缺少规范证据时不得声称视觉合规。复用 Client SDK 与平台领域：原生渠道调用放 SDK Adapter，业务 App 只组合 SDK、展示交互结果、保存可恢复订单上下文并按服务端权益开放能力。新增用户文案遵守目标项目国际化；中国渠道在既有隐私同意后的入口才可初始化支付 SDK，并复核最终原生产物的自动初始化行为。
7. 同一登录用户恢复其订单与支付尝试；APP SDK 回调仅代表交互结果。服务端确认待完成时保留 pending，不因超时、返回应用或 SDK `9000` 显示到账。业务后端仍校验平台权益；退款/撤销后的权益同样读取平台。首笔支付与代扣签约分别确认；单渠道签约失败不改写订阅商品、不阻断可用的普通支付、不清空其他渠道协议。
8. 运行平台、SDK、App 的相称测试与正式身份构建检查，再执行真机/渠道验收。记录支付、取消、重复操作、断网、延迟通知、补单、退款与账单核对；区分 Sandbox 与生产。需要 Owner 执行的真实交易动作交接具体订单与操作，随后读取服务端结果完成验收。
9. 更新目标 Manifest 暴露的支付 Knowledge，记录环境、AppID、来源 ref、非敏感配置引用、命令与实际验证结果。通用缺口回补公共平台/SDK；不将样板 App 私有商品、价格、账号或密钥写进本 Skill。

## 完成标准

- 正式产品身份、渠道可调用状态、registration 与商品绑定有实际证据。
- 真实设备能发起支付，平台服务端确认并履约，重新登录后权益仍正确；取消、恢复和退款按渠道实际能力通过。
- 购买协议官网正文、版本与购买页一致，重要条款显著提示，同意证据可关联订单；变更不追溯减损已购权益。
- 支付相关页面与当前 App 视觉一致，并符合 `fl-ui-design-system`；按其要求核验主题、文字缩放、窄屏及适用交互状态，保留截图或组件预览证据。
- 新 App 的应用层不新增支付/订单/退款领域，实现依赖可获取的公共 SDK 与平台契约。

## 失败处理

- 身份、渠道权限、SDK 能力或真实配置缺失时记录具体缺口，继续独立工作；禁止用网页请求假装 APP 支付或用客户端字段制造付款成功。
- 未完成真实验收使用 `validated-with-follow-up` 并列出剩余证据，不宣称支付接入完成；保持现有订单、通知、凭据与恢复入口。
