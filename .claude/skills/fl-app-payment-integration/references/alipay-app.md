# 支付宝 APP 支付接入

## 读取顺序

先读取目标 App 的支付宝申请资料、正式签名与 canonical App Link，再读取固定 ref 的 Shared Platform：

- `docs/runbooks/payment-provider-application-integration.md`
- `docs/runbooks/payment-provider-sandbox-validation.md`
- `docs/contracts/v1/schemas/commerce.schema.json` 与实际 Alipay Adapter

然后核查对应 Client SDK 的 Flutter commerce/payment 与 native payment 包。引用代表已验证实现的 ref；本地未发布能力必须明确为候选，不能给后续 App 一个不可获取的依赖 ref。

## 渠道与身份

- 区分商户 APP 支付签约、移动应用创建、接口加签配置、应用审核上线四个状态；分别保存证据。
- 复核正式 Android applicationId 与证书 MD5、iOS Bundle ID、应用图标与名称。填写资料沿用 [Flutter 身份与 App Link 契约](../../fl-ai-coding-delivery/references/domain-flutter-architecture.md) 第 7.1 节。
- 签约自动创建的基础应用和业务移动应用是不同身份；不得因前者上线而认定后者可正式调用。
- 从组织资产定位账号与既有密钥恢复入口，优先检查存在性，不回显值；没有现有密钥时再明确需要的创建/配置动作，遵守宿主凭据与外部操作限制。
- 确认是普通单次购买还是自动扣款；APP 支付开通不证明代扣协议、自动续费能力或平台 `RECURRING` 已具备。

## 计费模式

以固定平台版本的契约为准。具备 `PREPAID` 的平台中，手动月付采用按期预付，服务端确认后授予月周期权益；同套餐提前续费延长原到期时间，到期后购买从当前时间开始。`ONE_TIME` 在现有平台是无期限权益，不得用来冒充月订阅；`SUBSCRIPTION` 的首笔支付与代扣签约分别核查；只有真实渠道代扣能力和有效协议才能标为自动续费可用，不得给支付宝虚假配置 `RECURRING`。商品和渠道绑定的 billingMode 必须一致。

渠道不具备代扣能力时单独记录该渠道签约失败；若支持普通 APP 收款，仍可发起首笔支付，不以代扣失败阻断普通支付。平台候选实现通过支付尝试的 `renewalAgreementStatus=FAILED` 与 `renewalAgreementFailureCode=PAYMENT_PROVIDER_CAPABILITY_UNSUPPORTED` 持久化和返回结果；固定 ref 未包含此契约时先补齐公共实现，不能假定已发布。支付状态与代扣状态分别展示，空状态或查询失败不表示签约成功。保留其他渠道的订阅与代扣配置及已有协议；不得自动修改共享价格选项或改为 PREPAID。PREPAID 仅在 Owner 明确选择独立按期购买时配置。

按期预付须覆盖首次购买、提前续期、过期后续期、重复回调和月末边界；页面明确手动续费，不承诺自动扣款。是否限制功能以 Owner 权益决定为准，不因商品付费自动给现有功能加门禁。

## 平台与 SDK 契约核查

- APP 使用 `alipay.trade.app.pay` 与 `QUICK_MSECURITY_PAY`，由服务端 RSA2 签名；网页的 `alipay.trade.page.pay` / `FAST_INSTANT_TRADE_PAY` 不能作为替代。
- APP 会话必须输出原生 SDK 可接受的签名订单串，SDK 在后台线程执行官方支付调用；业务 App 不拼接订单串，不持有商户私钥。
- 明确支付交互场景，并将其纳入幂等摘要，避免同一 Key 混用网页和 APP 会话。
- 应用级 `appId`、商户私钥、支付宝公钥使用运行时 Secret 引用。密钥模式与证书模式的实现不能混用；以当前 Adapter 支持的配置为准。
- 交易异步通知由实际支付请求的 `notify_url` 指向平台 canonical 通知入口；后台「应用网关」是另一类平台消息入口，未设置应用网关不等于交易通知 URL 缺失。
- 支付宝通知在验签、订单归属核对和业务处理完成后返回 HTTP 200、`text/plain`，响应体必须恰好为 `success`；已处理的重复通知同样确认，处理失败不能返回成功。不能沿用平台通用的 202/JSON 响应作为支付宝确认。依据：[支付宝异步通知说明](https://help.alipay.com/support/help_detail.htm?help_id=397355)。
- 逐一核实签名、金额/币种、应用与订单归属。渠道查询的 `WAIT_BUYER_PAY` 和尚未建立交易不能推进终态失败；查询成功与通知均通过同一平台事件/权益履约管道。
- 在原生调起前等待持久化 orderId/attemptId；按应用与账号隔离记录，并能枚举该账号待恢复订单。原生异常仍向平台对账；取消后读取平台终态，避免覆盖已付款结果。记录 SDK 会话建立后可恢复的 orderId/attemptId；重启与重新登录后根据当前用户恢复。轮询有界，超时保留 pending，并提供再次查询入口。

## 真机验收证据

每份记录至少包含环境、应用、平台/SDK/App ref、商品/权益、正式包身份、readiness、场景结果及可关联的脱敏证据。完整渠道交易号、签名订单串、私钥、Token 和原始回调不进入知识资产。

| 场景 | 应观察的结果 |
|---|---|
| 正常付款 | 原生 SDK 可拉起；服务端确认订单；权益只履约一次；业务后端开放对应能力 |
| 代扣失败 | 首笔支付与渠道签约结果分别确认；订阅模式保持；代扣失败不清空其他渠道协议，已有渠道仍可续费 |
| 客户端伪成功 | `9000` 或回跳参数无法独立把平台订单标为 PAID |
| 取消 | App 可返回并显示相应交互状态；最终订单以渠道查询/关闭结果为准 |
| 断网/杀进程 | 可恢复既有订单；不重复建单或重复付款；恢复后读取真实权益 |
| 延迟/重复通知 | 延迟时 pending；重复通知不重复履约 |
| 补单 | 仅本人订单可发起查询；查询尚待支付时不误失败；已付款时补齐权益 |
| 退款 | 平台退款状态与渠道一致；部分/全额退款按平台现行权益策略处理；不重复撤销 |
| 对账 | 金额、币种、商户及平台订单可对应渠道账单 |

本地测试、Sandbox 和生产分别报告，不能相互替代。

## 已有密钥复用

Owner 选择复用已有加签密钥对时，从既有受控私钥位置派生应用公钥，供新应用登记；服务端引用同一稳定私钥 Secret，不生成或迁移密钥。保留每个应用自己的 AppID、registration 与通知 URL。应用公钥用于平台验证应用签名，支付宝公钥用于服务端验签，两者不可混用。将新应用下载的支付宝公钥规范化为 DER 后与现有验签公钥比较：内容相同时可共用既有引用，不同时使用该应用自己的验签引用；不能仅因共用应用私钥而推断支付宝公钥相同。知识中记录凭据位置、恢复命令、比较结果及真实交易证据，不记录私钥值。

## 创建阶段的公钥与人工交接

1. Owner 已决定同一组织应用共用现有 RSA2 加签方式时，复用该决定与稳定私钥引用，不重新询问是否生成密钥。优先取得已登记、可验证来源的应用公钥；已有公开文件可直接规范化为 DER/PEM 并核对指纹。需要派生时只在已授权受控位置执行公钥导出，私钥不下载、不回显。缺少等价来源才说明具体缺口。
2. 能自动填写、下载、比较与配置时直接执行，省略 Downloads 产物交接，不要求 Owner 管理、保留或搬运中间文件；项目 Knowledge 只记录稳定引用、公开指纹与结果。只有确需人工粘贴/上传或 Owner 要求交付文件时，在 `~/Downloads/<projectId>支付宝/` 保存 `<应用名称>_应用公钥_RSA2.txt`（无 PEM 头尾、无空白的 Base64 文本）、同名 `.pem` 和 `填写说明.md`。说明含应用名称/AppID、所填字段、源公钥位置与 DER SHA-256、两类公钥区别、唯一下一人工动作及后续自动处理。覆盖前核对已有文件；不同身份材料保留，不静默覆盖。该目录只放公开材料和说明，不放私钥、密码或验证码。
3. 应用创建后继续到「开发设置 → 接口加签方式 → 密钥 / RSA2 → 上传应用公钥」。在宿主允许的范围内自动填入刚验证的应用公钥；宿主要求当次确认时，先展示具体 AppID、复用对象和待提交页面，再取得确认。不要因公开资料可自动填写而把整段配置流程交给 Owner，也不得绕过宿主凭据、访问变更或验证限制。
4. Owner 必须本人完成的短信、支付密码、扫码或其他验证，交接时一次讲清当前步骤、需要填写/点击的内容及完成后的回复方式；不索要这些值。明确告诉 Owner：下载步骤取得的是「支付宝公钥」（服务端验签），不是前一步上传的「应用公钥」；通常只需保存到浏览器默认 Downloads，无需自行改名、移入仓库或配置服务端。工具支持下载时由 AI 完成下载，只有确需人工时才请 Owner 点击。
5. 操作前记录下载目录文件清单或使用浏览器 download 事件；Owner 回复已完成后重新检查真实页面与新下载文件，按新应用/AppID、文件时间和内容定位，不能直接取“最新一个公钥”猜测归属。找到后验证 RSA 公钥、规范化 DER、与既有支付宝验签公钥比较；自动配置所需材料进入已登记的消费位置，不把 Downloads 当运行时依赖。仅在前述人工/文件交付模式下保存 `<应用名称>_支付宝公钥_RSA2.txt/.pem` 到同一项目目录，并更新填写说明。记录指纹、相同/不同结果和稳定配置引用；不要让 Owner 再承担目录整理、重复录入或文件保管。清理 AI 本轮临时产物前确认已有稳定恢复入口，不删除既有凭据或其他下载。
6. 比较相同且复用已授权时，自动沿用既有服务端验签引用；不同则为该应用准备独立引用。继续在本次授权的部署/运行通道完成后续配置，未授权生产写入时先准备可审阅配置。AppID、通知地址和应用级 registration 仍各自独立。人工验证未完成、下载未定位或配置尚未应用时如实保留待办；下载成功不能替代加签配置、应用上线或支付验收。

## 纯血HarmonyOS

使用支付宝官方 [Harmony单框架集成流程](https://opendocs.alipay.com/open/0f71b5)，不要沿用旧HarmonyOS Java/Gradle HAR说明。公共原生插件声明ohos平台并封装官方OHPM `@cashier_alipay/cashiersdk`；当前候选固定15.8.44，升级须核对官方版本和真机条件。宿主entry配置querySchemes的alipays，在隐私同意后的组合根注册插件和支付宝Adapter；服务端仍签发NATIVE_APP订单串。

登记BundleName和发布证书SHA-256摘要，按HarmonyOS固定签名契约复核最终HAP；调试摘要独立登记。Flutter宿主必须补齐官方SDK的H5回退容器：Navigation包含FlutterPage，通过系统路由表承载SDK自带的alipay/cashier/H5Page，调用payWithNav并启用未安装客户端时H5回退。宿主返回键交由SDK目的页处理；不得因未安装支付宝直接拒绝付款。订单仍为服务端签发NATIVE_APP会话，SDK内部H5回退不等于切换为商家网页支付接口。SDK客户端结果、超时和系统唤端取消仍通过既有订单恢复及服务端确认流程处理；不记录订单串和结果正文。真实付款由Owner执行，随后核对服务端履约。
